# pragma.component-ecs decisions

ADR log. A decision changes only through a new entry with a reason (the old one is not deleted, it is marked "superseded by #N").

| # | Decision | Choice | Why | Date |
|---|---------|-------|--------|------|
| 1 | Component boundaries | An ECS: entities, components, storage, queries, systems, resources, commands, events. **No** rendering, windowing, input, asset loading, App/plugin framework, game loop | pragma.core DECISIONS #1 leaves the ECS to a layer above the core; the frame loop and the rest of the engine belong to a specific engine and must stay replaceable | 2026-10-14 |
| 2 | Relation to pragma.core | Depends on the `pragma_core` facade (1.x from crates.io) with `default-features = false`, enabling only what it uses (`jobs`, `graph`). No own thread pool or scheduler: systems become tasks of the pragma.core frame graph, parallel iteration goes through `ThreadPool::parallel_for` | One pool per process; the frame graph already validates resource conflicts at build time, which is exactly what system scheduling needs. The facade, not individual crates, per pragma.core's versioning policy | 2026-10-14 |
| 3 | Platforms and toolchain | The same as pragma.core: Windows and Linux (x86_64) in CI; edition 2024, MSRV 1.88, pinned 1.99.0 | The component ships together with the core; diverging toolchains would only add friction | 2026-10-14 |
| 4 | Workspace and versions | A Cargo workspace (`crates/*`), one crate `pragma_ecs` for now; all crates share one version (lockstep), internal dependencies `=X.Y.Z`. Starting at 0.0.1, `publish = false` until the API review | The same policy as pragma.core #33/#42; splitting into crates happens when a layer boundary appears, not in advance | 2026-10-14 |
| 5 | Dependency purity | Pure Rust only, checked by `cargo deny` and `tools/audit_workspace.py` (copied from pragma.core). `generator` (via `pragma_sync` → `loom`, only under `cfg(loom)`) is accepted in `[purity.accepted]` | The same rule as pragma.core #4; the `loom` path is inherited from pragma.core #7/#12 and never reaches users' binaries | 2026-10-14 |
| 6 | `unsafe` policy | `#![forbid(unsafe_code)]` in every crate at the start; `unsafe_allowed` is empty. Type-erased component storage will likely need `unsafe`: it is introduced by a separate decision, in a dedicated crate, with a budget in `layers.toml`, `// SAFETY:` on every block and Miri in CI | Confines the risk, as pragma.core #6/#27 did; the need is decided when the storage design (roadmap M1) is chosen, not in advance | 2026-10-14 |
| 7 | Documentation language | English everywhere: README, `docs/`, this log, rustdoc, comments | The same as pragma.core #43 | 2026-10-14 |
| 8 | Storage model (M1) | **Archetype tables**: entities with the same component set share a table, one column per component type, rows parallel to the table's entity list; insert/remove of a component moves the entity to the neighbouring table, transitions are cached per table. `Component` is a blanket trait over `Send + Sync + 'static`. Sparse-set storage may be added later as an opt-in per type (hybrid) by a new decision | Queries (M2) iterate dense slices without a join, which is the hot path of a frame; archetype ids are assigned in creation order, so the layout is deterministic. Structural changes cost O(number of components), acceptable for M1; a hybrid in the first milestone would double the code before benchmarks (M5) show a need. A blanket `Component` needs no derive; per-type configuration (for a hybrid) would mean an explicit impl, a breaking change allowed before 1.0 | 2026-10-14 |
| 9 | `unsafe` in storage (M1) | **None.** A column is a `Box<dyn Column>` implemented for `Vec<T>`: the column is boxed, not every component; typed access is one `downcast` per column, then a plain `&[T]` / `&mut [T]`. DECISIONS #6 stays as is: `unsafe_allowed` is empty, `#![forbid(unsafe_code)]` in `pragma_ecs`, no Miri job needed. Revisited only with M5 benchmark data, by a new decision | A byte-blob column (bytes + `Layout` + drop fn) would save a virtual call per component on structural changes, but iteration speed is the same once the column is downcast, and it would bring UB risk, a separate crate, a budget and Miri into the first milestone | 2026-10-14 |
| 10 | `Entity` id (M1) | Our own `Entity { index: u32, generation: u32 }` and allocator, modeled on `pragma_core`'s `HandlePool` (`try_reserve` for the slots and the free list, `free` never allocates, a slot with an exhausted generation is retired forever), plus `to_bits` / `from_bits`. `Handle`/`HandlePool` are not reused | `HandlePool` has no iteration over live ids, no raw-bits round trip (serialization, networking) and no id reservation through `&self`, which deferred spawning from systems (M4) needs; adding them means a pragma.core 1.x release. A `pragma_core` type in our public API would also tie our semver to it (pragma.core reliability §8) | 2026-10-14 |
| 11 | OOM test allocator | `crates/pragma_ecs/tests/oom.rs`: a failing `GlobalAlloc` (7 `unsafe`, in `[unsafe_budget]`), a copy of `pragma_base/tests/oom.rs` | An allocator failure can be tested only with a global allocator (pragma.core #37); it is test code in its own binary that never reaches the library, which keeps `#![forbid(unsafe_code)]` (#9) | 2026-10-14 |
| 12 | Query API (M2) | A query is a state object `Query<Q, F = ()>`, built once with `Query::new()` and not borrowing the world: `iter(&World)` (read-only `Q`), `iter_mut(&mut World)`, `par_for_each` / `par_for_each_mut`. `Q` is `&T`, `&mut T`, `Option<&T>`, `Entity` or a tuple of them (up to 8); `F` is `With<T>`, `Without<T>` or a tuple. It caches the ids of the matching archetypes and on every call checks only the archetypes created since (they are never removed); the cache is tied to a world id and is rebuilt for another world. `QueryData` / `QueryFilter` are sealed | Systems (M3) need a long-lived query that carries its declared access and does not rescan every table each frame, like `QueryState` in bevy or `PreparedQuery` in hecs. Sealing keeps the fetch machinery private, so it can change (e.g. by M5 benchmarks) without a breaking change | 2026-10-14 |
| 13 | Disjoint column borrows (M2) | **No `unsafe`.** One pass of `columns.iter_mut()` offers every column of a table to the query's elements: a write takes the `&mut` column, a read turns it into a shared reference that further reads copy. Each element downcasts its column once per table into `&[T]` / `&mut [T]` and the rows are zipped slice iterators. DECISIONS #9 stands, `#![forbid(unsafe_code)]` stays | The borrow checker itself proves that no two `&mut` alias; the cost is O(columns × query elements) per table, nothing per row. Raw column pointers (a separate `unsafe` crate under #6) would not make iteration faster once the slices are taken | 2026-10-14 |
| 14 | Declared access (M2) | `Access`: a sorted list of (component type, its name, `Read`/`Write`), built by `Query::new()`. `&T` and `Option<&T>` read, `&mut T` writes; `With`/`Without` and `Entity` declare nothing. A write of a type together with any other access to it (`(&A, &mut A)`, `(&mut A, &mut A)`, `(Option<&A>, &mut A)`) is `EcsError::ConflictingAccess { component }`; repeated reads are allowed. `Access::conflict` compares two accesses (for M3) | Aliasing becomes a typed error at construction instead of a silently empty or panicking query; repeated reads are harmless and allowed by bevy and hecs too. The list grows through `try_reserve` | 2026-10-14 |
| 15 | Parallel iteration (M2) | The work unit is a chunk of rows: chunk size = `grain.chunk_size(total matching rows)` (`pragma_core` `Grain`), every matching table is split into chunks of that size, and the chunk list (`try_reserve` → `OutOfMemory`) goes to `ThreadPool::parallel_for` with `Grain::Fixed(1)`. A chunk holds the column slices of its rows, so it is `Send` because components are `Send + Sync`; the closure is `Fn(Item) + Sync`. A task failure is the new `EcsError::Job { source: JobError }` | One big table, the common case, still spreads over all workers; the split depends only on the data, not on the worker count, so results are the same on 1 and N workers (pragma.core determinism rule). `ThreadPool` and `Grain` in the signature are the core types DECISIONS #2 builds on | 2026-10-14 |
| 16 | Benchmarks | `criterion` 0.8 (the version pragma.core uses) as a dev dependency of `pragma_ecs`, `benches/query.rs`. It pulls `alloca`, which builds C via `cc`: accepted in `[purity.accepted]` of `layers.toml`, as in pragma.core #17/#21; `deny.toml` already excludes the dev graph | Iteration is the hot path (CONTRIBUTING: a benchmark is mandatory); criterion is the tool pragma.core's methodology and bench gate are built on (docs/perf.md). It never reaches users' binaries | 2026-10-14 |
