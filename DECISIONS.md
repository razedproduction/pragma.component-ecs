# pragma.component-ecs decisions

ADR log. A decision changes only through a new entry with a reason (the old one is not deleted, it is marked "superseded by #N").

| # | Decision | Choice | Why | Date |
|---|---------|-------|--------|------|
| 1 | Component boundaries | An ECS: entities, components, storage, queries, systems, resources, commands, events. **No** rendering, windowing, input, asset loading, App/plugin framework, game loop | pragma.core DECISIONS #1 leaves the ECS to a layer above the core; the frame loop and the rest of the engine belong to a specific engine and must stay replaceable | 2026-10-14 |
| 2 | Relation to pragma.core | Depends on the `pragma_core` facade (1.x from crates.io) with `default-features = false`, enabling only what it uses (`jobs`, `graph`). No own thread pool or scheduler: systems become tasks of the pragma.core frame graph, parallel iteration goes through `ThreadPool::parallel_for` | One pool per process; the frame graph already validates resource conflicts at build time, which is exactly what system scheduling needs. The facade, not individual crates, per pragma.core's versioning policy | 2026-10-14 |
| 3 | Platforms and toolchain | The same as pragma.core: Windows and Linux (x86_64) in CI; edition 2024, MSRV 1.88, pinned 1.99.0 | The component ships together with the core; diverging toolchains would only add friction | 2026-10-14 |
| 4 | Workspace and versions | A Cargo workspace (`crates/*`), one crate `pragma_ecs` for now; all crates share one version (lockstep), internal dependencies `=X.Y.Z`. Starting at 0.0.1, `publish = false` until the API review | The same policy as pragma.core #33/#42; splitting into crates happens when a layer boundary appears, not in advance | 2026-10-14 |
| 5 | Dependency purity | Pure Rust only, checked by `cargo deny` and `tools/audit_workspace.py` (copied from pragma.core). `generator` (via `pragma_sync` → `loom`, only under `cfg(loom)`) is accepted in `[purity.accepted]` | The same rule as pragma.core #4; the `loom` path is inherited from pragma.core #7/#12 and never reaches users' binaries | 2026-10-14 |
| 6 | `unsafe` policy | `#![forbid(unsafe_code)]` in every crate at the start; `unsafe_allowed` is empty. Type-erased component storage will likely need `unsafe`: it is introduced by a separate decision, in a dedicated crate, with a budget in `layers.toml`, `// SAFETY:` on every block and Miri in CI | Confines the risk, as pragma.core #6/#27 did; the need is decided when the storage design (roadmap M1) is chosen, not in advance | 2026-10-14 |
| 7 | Documentation language | English everywhere: README, `docs/`, this log, rustdoc, comments | The same as pragma.core #43 | 2026-10-14 |
| 8 | Storage model (M1) | **Archetype tables**: entities with the same component set share a table, one column per component type, rows parallel to the table's entity list; insert/remove of a component moves the entity to the neighbouring table, transitions are cached per table. `Component` is a blanket trait over `Send + Sync + 'static`. Sparse-set storage may be added later as an opt-in per type (hybrid) by a new decision | Queries (M2) iterate dense slices without a join, which is the hot path of a frame; archetype ids are assigned in creation order, so the layout is deterministic. Structural changes cost O(number of components), acceptable for M1; a hybrid in the first milestone would double the code before benchmarks (M5) show a need. A blanket `Component` needs no derive; per-type configuration (for a hybrid) would mean an explicit impl, a breaking change allowed before 1.0 | 2026-10-14 |
| 9 | `unsafe` in storage (M1) | **None.** A column is a `Box<dyn Column>` implemented for `Vec<T>`: the column is boxed, not every component; typed access is one `downcast` per column, then a plain `&[T]` / `&mut [T]`. DECISIONS #6 stays as is: `unsafe_allowed` is empty, `#![forbid(unsafe_code)]` in `pragma_ecs`, no Miri job needed. Revisited only with M5 benchmark data, by a new decision | A byte-blob column (bytes + `Layout` + drop fn) would save a virtual call per component on structural changes, but iteration speed is the same once the column is downcast, and it would bring UB risk, a separate crate, a budget and Miri into the first milestone | 2026-10-14 |
| 10 | `Entity` id (M1) | Our own `Entity { index: u32, generation: u32 }` and allocator, modeled on `pragma_core`'s `HandlePool` (`try_reserve` for the slots and the free list, `free` never allocates, a slot with an exhausted generation is retired forever), plus `to_bits` / `from_bits`. `Handle`/`HandlePool` are not reused | `HandlePool` has no iteration over live ids, no raw-bits round trip (serialization, networking) and no id reservation through `&self`, which deferred spawning from systems (M4) needs; adding them means a pragma.core 1.x release. A `pragma_core` type in our public API would also tie our semver to it (pragma.core reliability §8) | 2026-10-14 |
| 11 | OOM test allocator | `crates/pragma_ecs/tests/oom.rs`: a failing `GlobalAlloc` (7 `unsafe`, in `[unsafe_budget]`), a copy of `pragma_base/tests/oom.rs` | An allocator failure can be tested only with a global allocator (pragma.core #37); it is test code in its own binary that never reaches the library, which keeps `#![forbid(unsafe_code)]` (#9) | 2026-10-14 |
| 12 | Query API (M2) | A query is a state object `Query<Q, F = ()>`, built once with `Query::new()` and not borrowing the world: `iter(&World)` (read-only `Q`), `iter_mut(&mut World)`, `par_for_each` / `par_for_each_mut`. `Q` is `&T`, `&mut T`, `Option<&T>`, `Entity` or a tuple of them (up to 8); `F` is `With<T>`, `Without<T>` or a tuple. It caches the ids of the matching archetypes and on every call checks only the archetypes created since (they are never removed); the cache is tied to a world id and is rebuilt for another world. `QueryData` / `QueryFilter` are sealed | Systems (M3) need a long-lived query that carries its declared access and does not rescan every table each frame, like `QueryState` in bevy or `PreparedQuery` in hecs. Sealing keeps the fetch machinery private, so it can change (e.g. by M5 benchmarks) without a breaking change | 2026-10-14 |
| 13 | Disjoint column borrows (M2) | **No `unsafe`.** One pass of `columns.iter_mut()` offers every column of a table to the query's elements: a write takes the `&mut` column, a read turns it into a shared reference that further reads copy. Each element downcasts its column once per table into `&[T]` / `&mut [T]` and the rows are zipped slice iterators. DECISIONS #9 stands, `#![forbid(unsafe_code)]` stays | The borrow checker itself proves that no two `&mut` alias; the cost is O(columns × query elements) per table, nothing per row. Raw column pointers (a separate `unsafe` crate under #6) would not make iteration faster once the slices are taken | 2026-10-14 |
| 14 | Declared access (M2) | `Access`: a sorted list of (component type, its name, `Read`/`Write`), built by `Query::new()`. `&T` and `Option<&T>` read, `&mut T` writes; `With`/`Without` and `Entity` declare nothing. A write of a type together with any other access to it (`(&A, &mut A)`, `(&mut A, &mut A)`, `(Option<&A>, &mut A)`) is `EcsError::ConflictingAccess { component }`; repeated reads are allowed. `Access::conflict` compares two accesses (for M3) | Aliasing becomes a typed error at construction instead of a silently empty or panicking query; repeated reads are harmless and allowed by bevy and hecs too. The list grows through `try_reserve` | 2026-10-14 |
| 15 | Parallel iteration (M2) | The work unit is a chunk of rows: chunk size = `grain.chunk_size(total matching rows)` (`pragma_core` `Grain`), every matching table is split into chunks of that size, and the chunk list (`try_reserve` → `OutOfMemory`) goes to `ThreadPool::parallel_for` with `Grain::Fixed(1)`. A chunk holds the column slices of its rows, so it is `Send` because components are `Send + Sync`; the closure is `Fn(Item) + Sync`. A task failure is the new `EcsError::Job { source: JobError }` | One big table, the common case, still spreads over all workers; the split depends only on the data, not on the worker count, so results are the same on 1 and N workers (pragma.core determinism rule). `ThreadPool` and `Grain` in the signature are the core types DECISIONS #2 builds on | 2026-10-14 |
| 16 | Benchmarks | `criterion` 0.8 (the version pragma.core uses) as a dev dependency of `pragma_ecs`, `benches/query.rs`. It pulls `alloca`, which builds C via `cc`: accepted in `[purity.accepted]` of `layers.toml`, as in pragma.core #17/#21; `deny.toml` already excludes the dev graph | Iteration is the hot path (CONTRIBUTING: a benchmark is mandatory); criterion is the tool pragma.core's methodology and bench gate are built on (docs/perf.md). It never reaches users' binaries | 2026-10-14 |
| 17 | System representation (M3) | A system is a plain function whose parameters are sealed `SystemParam`s: `View<Q, F>` (a query over the frame's world), `Res<T>`, `ResMut<T>`, up to 8 of them; it returns `()` or `Result<(), E>` for any error type `E` (as pragma.core tasks do: a game's own errors, not only `EcsError`, whose variants users cannot construct). Its `Access` is the union of its parameters' accesses (components and resources kept apart); a write together with any other use of the same type inside one system is `EcsError::ConflictingAccess` / `ConflictingResourceAccess` when the system is added. The parameters' state (query caches) lives with the system in the schedule | The access is derived from the signature, so a system cannot use data it did not declare, and mistakes surface at registration rather than as `UndeclaredAccess` in a frame; the shape is the one bevy users know. Sealing keeps the parameter machinery internal (like #12). Closures with an explicit access list and a `System` trait on structs were rejected: the first moves errors to run time, the second is verbose for every system | 2026-10-14 |
| 18 | The world in the frame graph (M3) | **Lend the columns, no `unsafe`.** Before a frame, every table's `Vec<T>` of each component type some system uses is swapped (`mem::swap`, no allocation) into a graph resource `Columns<T>` (one slot per table), and the world itself (table types and entity lists, the lent columns left empty) becomes a graph resource every system reads. Component access is declared as `reads`/`writes::<Columns<T>>()`, so pragma.core's per-resource `RwLock` hands disjoint systems their columns in parallel. After the frame (also after a failed one) everything is swapped back. No structural changes during a frame (deferred commands are M4). DECISIONS #9 and #13 stand | Systems with disjoint access really run in parallel through the graph's own locking, the M1 storage is unchanged, and the cost is O(tables × lent types) pointer swaps per frame; the slots grow (`try_reserve`) only when new tables appear. The whole world as one resource would serialize every writing system; per-column locks in storage would change #9/#13; raw pointers would need an `unsafe` crate under #6 | 2026-10-14 |
| 19 | Order of conflicting systems (M3) | Strict by default: two systems whose accesses conflict without an explicit order fail `ScheduleBuilder::build` with `EcsError::AmbiguousOrder { first, second, data }` (from pragma.core `GraphError::AmbiguousOrder`, the lent-column resource named by its component type). Order is `SystemConfig::after` / `before` (`add_system_with`); `ScheduleBuilder::ordered()` is pragma.core's `ordered` mode, where the registration order settles conflicts | The roadmap's guarantee: a data race becomes a build error naming both systems and the data. `ordered()` makes porting a sequential loop of systems trivial while independent systems still run in parallel, at no cost since pragma.core already has it | 2026-10-14 |
| 20 | Resources (M3) | Singletons live in the `World` (`insert_resource`, `resource`, `resource_mut`, `remove_resource`, `contains_resource`; `Resource` is a blanket trait over `Send + Sync + 'static`), stored in a `pragma_core` graph `Resources` that the frame graph runs over directly. Systems take `Res<T>` / `ResMut<T>`, declared as `reads`/`writes::<T>()`. A resource a system needs but the world lacks is `EcsError::MissingResource { system, resource }` before any system of the frame runs. Inserting a resource allocates one box infallibly (fixed size, like a new column's box in M1) | One owner for all the state a schedule runs over; no extra argument to `run`; pragma.core's check for missing resources comes for free. A separate resource object was rejected as an extra parameter everywhere for flexibility (extract copies) nobody needs yet | 2026-10-14 |
| 21 | Schedule lifetime and errors (M3) | `Schedule::builder()` → `add_system` → `build()` once; `Schedule::run(&mut World, &ThreadPool)` every frame; a changed set of systems means a new schedule. `run` errors map to new `#[non_exhaustive]` variants: `MissingResource`, `SystemFailed { system, message, source }` (the message of the error the system returned, and the error itself if it was an `EcsError`), `SystemPanicked { system, message }`; a pool failure is `EcsError::Job`; other graph errors (cycle, unknown dependency, duplicate name, too large) are `EcsError::Schedule { source: GraphError }` | The pragma.core model (#2): validate once at startup, run without rebuilding. Typed variants for what a game reacts to; the rest keeps pragma.core's own error as its source instead of duplicating its variants | 2026-10-14 |
| 22 | Vertical-slice example (M3) | A workspace crate `examples/ecs_sim` (layer 1 in `layers.toml`, `publish = false`, no new dependencies), modeled on pragma.core's `frame_sim`: N entities, several systems on one schedule, an FNV state hash per tick; its tests and `--verify` compare the hashes on 1, 2 and N workers | The roadmap's slice: world → queries → systems on the frame graph in one runnable program, and the determinism check every later milestone is verified on | 2026-10-14 |
| 23 | Deferred commands (M4) | A `Commands` system parameter records spawn / despawn / insert / remove into a queue that lives in the system's own state, so it declares no access and never orders systems. **Deferred ids:** `Commands::spawn` returns an `EntityCommands` builder for the new entity, whose real `Entity` is allocated only when the queue is applied; commands on it inside the same queue address it by its position. Inserted values go into typed lanes (a `Vec<T>` per component type behind one `Box<dyn …>`, created once per type and kept between frames); every growth is `try_reserve` → `EcsError::OutOfMemory` returned by the call that records the command. No id reservation through `&self` | Per-system queues need no lock and no graph access, so systems with commands still run in parallel. An id allocated during the frame would depend on which worker ran first (two parallel spawning systems), breaking the 1-vs-N-workers hash; allocating at the sync point in a fixed order makes ids deterministic by construction. Reservation through a shared allocator (DECISIONS #10 anticipated it) would make every system with `Commands` conflict with every other to stay deterministic. The cost: a new entity's id is not known before the end of the frame | 2026-10-14 |
| 24 | The sync point (M4) | One per frame, at the end of `Schedule::run`, after the columns are returned: first every event type the schedule uses is updated (`Events<T>::update`), then the deferred buffers of the systems are applied **in system registration order**, a system's parameters in parameter order, a queue's commands in the order they were recorded. Commands are applied with the world's ordinary operations. Stages are several schedules run one after another; explicit apply points inside one schedule are not provided (they can be added later without a breaking change) | The order depends only on the schedule and on what each system recorded, never on the worker count or timing, so the world after a frame is the same on 1 and N workers. One point per `run` keeps the frame one frame-graph run; splitting a schedule into several graphs would complicate `after`/`before` across the split for no current need | 2026-10-14 |
| 25 | Command failures (M4) | **Lenient.** A command on an entity that is no longer alive (despawned earlier, also by another system's command) is a no-op, the value it carried is dropped. Any other failure while applying (`OutOfMemory`, `CapacityExhausted`) stops the application: the commands already applied stay applied, the failing one and all later ones (of every system) are discarded, and `run` returns the new `EcsError::CommandFailed { system, source }`. The buffers of a system that returned an error or panicked are discarded, the others are applied; if the frame itself failed, its error is returned and a command failure is not reported over it. Each world operation stays atomic (M1) | Two systems despawning the same entity, or inserting into an entity another system despawns, are ordinary races of game logic, not errors; making them errors would force every game to order such systems. Out of memory cannot be ignored, and discarding the rest keeps buffers bounded instead of retrying an ever-growing backlog. A failed system may have recorded half of its intent, so its commands are not applied | 2026-10-14 |
| 26 | Events (M4) | `Events<T>`, a resource of the world with two buffers (the events of the last two sync points) and a running event id; `Event` is a blanket trait over `Send + Sync + 'static`. **Published at the sync point:** `EventWriter<T>` sends into a buffer in the system's own state (no graph access); at the sync point the schedule updates `Events<T>` (drops the older buffer) and appends every writer's events in registration order. `EventReader<T>` reads `Events<T>` (a resource read, so it conflicts only with explicit `ResMut<Events<T>>`) from a cursor kept in the system's state, reset for another world. The schedule creates `Events<T>` for every event type its systems use. Outside systems: `World::send_event`, `Events::update`, `EventCursor` | Writers and readers never conflict, so they run in parallel and the delivery order is fixed by construction (registration order). The price is a latency of exactly one frame, which a deterministic simulation accepts. Two buffers let a reader that runs every frame see every event exactly once and tolerate one missed frame (or two schedules sharing an event type) | 2026-10-14 |
| 27 | Change ticks (M4) | Every row of every column carries an added and a changed tick as **`u64`**, in two `Vec`s next to the values in the same column (`ColumnData<T>`; separate vectors, so that a write touches only the changed ticks), so ticks move with their rows and are lent to a frame together with the values (DECISIONS #18 unchanged otherwise). The world keeps a change tick: every mutating world operation takes a new tick. A frame takes one tick per system: base + the system's position in the schedule's stable topological order, so conflicting systems get ticks in their real order on any worker count; commands are applied after all of them. A system remembers the tick of its last run, a `Query` the world tick of its last call (both reset for another world); "changed since" means `tick > last_run`, and a first run sees every existing component as added and changed. No wraparound handling | u64 ticks never wrap in practice, so there is no periodic O(all rows) clamping pass, no frame spike and no rarely-taken path to test; a long-unused query stays correct. Ticks in the column keep every structural move and the lending swap a single operation per column. The cost is 16 bytes per component per row, and a write through `Mut` stores 8 bytes more (≈ +45 % on a memory-bound write-every-row benchmark, `docs/architecture.md`). Per-system ticks from the topological position are deterministic, unlike a shared atomic counter | 2026-10-14 |
| 28 | `Mut<T>` and change filters (M4) | `&mut T` in a query or view now yields **`Mut<'_, T>`** (`Deref` / `DerefMut`; `DerefMut` stamps the row's changed tick, so only rows really written count as changed); `World::get_mut` stamps eagerly and keeps returning `&mut T`; replacing a component through `insert` counts as a change. `Added<T>` and `Changed<T>` are row filters: per matching table, the query fills a reusable mask of passing rows from the tick columns (shared reads) **before** the data columns are borrowed, so `Query<&mut T, Changed<T>>` works without `unsafe`. A filter reads `T`: inside one query or view that read merges with a use of `T` by the data (a view looks the ticks up through its own guard); across views of a system and across systems the usual strict rules apply. With, Without and `()` stay table filters with no mask. DECISIONS #9, #13 and #18 stand: no `unsafe` | Precise change detection is what `Changed<T>` is for; a coarse "every row handed out mutably is changed" would make it useless after any mutable iteration. The wrapper is a breaking change (allowed before 1.0): passing an item to a `fn(&mut T)` needs `&mut *item`. A mask computed first is the safe way to read and later write the same tick column in one pass; its cost (one pass over the filtered tick columns plus a byte per row, reused between calls) is paid only by queries with change filters | 2026-10-14 |
| 29 | Determinism suite (M5) | `ecs_sim --suite` runs a fixed set of scenarios (seeds, entity counts including an empty world, a single entity and an odd count, entities spread over several tables, a lethal hazard that makes the frame heavy with commands and events, a calm one where change filters see few changes) on 1, 2 and N workers (N = the default worker count, no oversubscription) and requires the same per-tick hashes on every worker count. **Golden hashes are committed:** `examples/ecs_sim/golden.txt` holds, per scenario and tick count, a hash of the hashes of all ticks; the suite fails on a mismatch or a missing entry, and `--bless` rewrites the file. CI runs it in release on Windows and Linux with 200 ticks on every PR; the nightly workflow with 3000 ticks; a debug test runs the same scenarios, capped in size, across worker counts | The user's choice among three options (scenarios + golden / across worker counts only / the existing `--verify`). Comparing worker counts inside one run cannot see a hash that differs between Windows and Linux or a behaviour change nobody intended; the goldens catch both, and an intended change shows up as a reviewed diff of `golden.txt`. The simulation uses only IEEE-exact `f32` operations (no transcendental functions, no fused multiply-add), so the same goldens hold on every supported platform | 2026-10-15 |
| 30 | Fuzzing (M5) | **cargo-fuzz** in a separate `fuzz/` workspace (nightly, `libfuzzer-sys` is C++), as pragma.core #20: not a member of the main workspace, so it is part of neither users' dependency trees nor the `cargo deny` / audit graph (`libfuzzer-sys` is already in the audit's `DEV_TOOL_OK`). Three targets — `world_ops` (world operations and queries with table and row filters, sequential and parallel, against the `HashMap` oracle), `commands` (random command queues of several systems through a schedule against direct world operations) and `change_ticks` (`Added` / `Changed` against the per-entity tick oracle) — decode their input into the same operations the property tests generate; the oracles live in `crates/pragma_ecs/tests/common/` and are shared by both through `#[path]`. CI: 60 s per target on Linux in every PR that touches code; nightly 10 min per target with the corpus kept in the Actions cache and crashes uploaded as artifacts. On Windows the same oracles run through proptest | The user's choice among three options (cargo-fuzz / a pure-Rust `arbitrary` driver / proptest only). Coverage-guided fuzzing finds what random generation does not, and keeping the C++ in a dev-only workspace repeats a decision pragma.core already made and documented; one oracle per property means a fuzz finding becomes a proptest regression without translating it | 2026-10-15 |
| 31 | Baseline benchmarks (M5) | A separate `baseline/` workspace (`publish = false`, like `fuzz/`) with `criterion`, **`hecs` 0.11** and **`bevy_ecs` 0.20** (`default-features = false`, `std` only) next to `pragma_ecs`, the same workloads on all three in one criterion group: spawning 10 000 entities with two components, iterating 100 000 `(&mut Position, &Velocity)`, iterating 20 entities in each of 26 tables, adding and removing a component on 10 000 entities, despawning 10 000. Results go into `docs/architecture.md`; CI only builds it (PRs that touch code), the nightly workflow runs it and writes the table into the job summary. Its `Cargo.lock` is committed. The main workspace, its MSRV check, `cargo deny` and the audit never see these crates | The user's choice among three options (a separate workspace / dev dependencies of `pragma_ecs` / hecs only). `bevy_ecs` 0.20 needs Rust 1.95 (our MSRV is 1.88) and pulls dozens of crates; in the main lock file shared dependencies would be unified with versions that could break the MSRV build. Both are pure Rust under MIT OR Apache-2.0 and are only benchmark baselines, never users' dependencies | 2026-10-15 |
| 32 | Bench gate (M5) | `tools/bench_gate.py`, adapted from pragma.core (#34 there): in PRs on Windows and Linux the PR base and head are built into different target directories, measurements interleave base/head for 3 rounds, the best criterion median across rounds counts. Gated: the `pragma_ecs` benches `query`, `schedule`, `commands` and `change`, each against its reference in the same bench (a plain `Vec`, sequential queries, direct world operations, a plain read): a measurement fails if `head/base > 1.1` **and** normalized by its reference's shift `> 1.1`; `ecs_sim` ms/tick (1 and N workers) without a reference fails above `1.1 + its own run noise`. A `changes` job skips the gate, fuzzing, semver-checks and the baseline build on PRs that touch only `*.md` / `docs/` (pragma.core #45). No stored baselines, no external services | The user's choice (A/B on the same runner). Shared runners differ by 10–20 % between machines, so only an interleaved A/B in one job with a reference the change cannot affect separates a regression from noise; the methodology and the script already exist in pragma.core | 2026-10-15 |
| 33 | Semver checks and the version (M5) | `cargo semver-checks -p pragma_ecs --baseline-rev <PR base>` in PRs on Windows and Linux (the package is named explicitly because `publish = false` crates are skipped by `--workspace`); the baseline is `main`, as in pragma.core #33. The workspace version becomes **0.5.0** in M5 (from 0.1.0; M2–M4 changed the API without a bump), without a tag: the owner tags and releases. The tool is a CI binary (`taiki-e/install-action`), not a dependency | The user's choice among three options (main + 0.5.0 / main + 0.1.0 / the last tag). Comparing with `main` catches a breaking change in the PR that introduces it; at 0.1.0 every later breaking change would fail until a bump, and comparing with v0.1.0 would let everything through since M2–M4 already broke it. 0.5.0 makes the version match the milestone, as pragma.core did | 2026-10-15 |
| 34 | Earlier decisions after the M5 benchmarks | **No change.** DECISIONS #9 / #13 (no `unsafe` in storage) and #27 (`u64` change ticks next to the values) stand; batching a spawn into its final table (a `Bundle` of components for `World` and `Commands`) is an API addition and goes to the M6 API review instead of M5. The baseline numbers (`baseline/`, 8 logical cores, Windows, medians, pragma_ecs / hecs / bevy_ecs): spawning 10 000 entities with two components 2.46 ms / 0.59 ms / 1.07 ms; iterating 100 000 `(&mut Position, &Velocity)` 322 µs / 204 µs / 348 µs (a plain `Vec` 258 µs); 20 rows in each of 26 tables 1.62 µs / 0.35 µs / 1.04 µs; adding and removing a component on 10 000 entities 3.06 ms / 1.85 ms / 2.59 ms; despawning 10 000 entities 277 µs / 344 µs / 874 µs | The user's choice among three options (record and move bundles to M6 / bundle spawns now / numbers only). Iteration is faster than `bevy_ecs`, which also stamps change ticks, and within the memory traffic of the extra tick store relative to `hecs`, which has no change detection; nothing points at the virtual call per column or at boxed columns, so `unsafe` storage would buy nothing measurable. The clear gap is spawning (no bundles: every `insert` moves the entity to the next table), which a new public API fixes, not a storage change; M6 reviews the API anyway | 2026-10-15 |
| 35 | Bundles (M6) | A sealed trait **`Bundle`**, implemented for tuples of 0 to 12 components (no derive, no new dependency). **Additive:** `World::spawn_bundle(bundle) -> Entity` creates the entity directly in its final table, `World::insert_bundle(entity, bundle)` moves it once to the table with all the bundle's types (components it already has are replaced in place and count as changed, new ones as added); `Commands::spawn_bundle` (returns `EntityCommands`), `Commands::insert_bundle` and `EntityCommands::insert_bundle` record the same, applied at the sync point. `spawn()` and `insert()` stay as they are. A bundle with the same type twice, `(A, A)`, is the new `EcsError::DuplicateComponent { component }` and changes nothing.
